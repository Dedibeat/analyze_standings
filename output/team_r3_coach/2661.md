### B. Cutting Chocolate — field 196/260 (cf 2007) — **AC 220.7' after 5 WA** (Tamir)
- **Idea:** n must be divisible by (p+1)(q+1)(r+1). The three dimensions are independent: sort by x,
  and the k-th cut lies between the (k·n/(p+1))-th and next point, so multiply the gap counts.
  **Then verify that every block really has the same count** (a 3-D bucket count; the editorial
  warns about exactly this). Tags: counting, sorting, verification.
- **Attempts:**
  1. 3191526 (51.8') WA: per-dimension product of gaps, with divisibility checked per dimension
     (`n % (p + 1) != 0 || n % (q + 1) …`), **no equal-count check**.
  2. 3191627 (65.6') WA: divisibility by the product. Still no check: the missing idea.
  3. 3192234 (141.3') WA: a new hierarchical approach (sort by x and split; inside each group sort by
     y and split; then z; intersect the allowed cut intervals). The approach is valid, but with
     p = 0 the x loop pushes no group starts, so `a2` stays empty.
  4. 3192623 (191.2') WA: divisibility checks split, `inf = 2e18`; the empty-`a2` bug remains.
  5. 3192772 (216.0') WA: `if(a2.empty()) a2 = {0}; … if(a3.empty()) a3 = {0};`. That is wrong
     for q = 0 with p > 0: then a3 must be all x-group starts, not {0}.
  6. 3192807 (220.7') AC: the start lists are accumulated (`a1 = a2; … a2.push_back(…)`).
- **Lessons:** (a) the first two WAs came from a missing verification step. "Do these independent
  choices really produce equal blocks?" should be asked before coding. (b) Edge cases p/q/r = 0 are
  the obvious tests for a "cuts in 3 dimensions" problem. (c) 169 minutes on the second-easiest
  problem: by ~100' a teammate should have re-read the statement with Tamir.

### G. Plus Xor — field 179/260 (cf 2047) — **AC 99.2' after 5 WA** (Erdene)
- **Idea:** if a ≡ c (mod b) and a ≤ c, add b repeatedly. The state (a mod 2^L, a mod b) with
  L = bit length of b determines everything. Run Dijkstra on the minimum reachable a. XOR can
  decrease a, but Dijkstra still works; alternatively rewrite the operations as +b and (⊕b)+b, since
  two XORs in a row cancel. Tags: shortest path on residues, bits.
- **Attempts:**
  1. 3191584 (61.1') WA, **wrong idea**: simulate only alternating +b/⊕b patterns with a visited
     set. `vector<vector<char>> vis((1ll << 10), …)` is indexed by `a & ((1ll << 11) - 1)`, which
     is out of bounds.
  2. 3191724 (79.7') WA: Dijkstra, but with
     `priority_queue<…, less<array<int,3>>>`, a **max-heap**, and the transition `(cur ^ b) + b`.
     It also prunes `cur > c`, which is invalid because XOR can make a smaller later.
  3. 3191747 (83.6') WA: transition changed to `cur ^ b`. Still a max-heap.
  4. 3191789 (89.6') WA: `greater<>` (min-heap), transition back to `(cur ^ b) + b`.
  5. 3191819 (92.9') WA: `len = 1ll << 11`, `if(cur1 < cur) cur1 += b;`.
  6. 3191865 (99.2') AC: `if(cur != dist[x][y]) continue;` (drops the `cur > c` prune), plain
     `cur ^ b`.
- **Lessons:** runs 2–5 **toggled the transition back and forth** (`(cur^b)+b` ↔ `cur^b`) without
  a local test. That is submission-driven debugging. The max-heap default of `priority_queue` is a
  classic C++ trap; the team library should have a typed Dijkstra.

### J. Subrectangle Count — field 90/260 (cf 2352) — **failed (2 in-contest runs; the QOJ board counts 1); upsolved by Dedi**
- **Idea:** x → x+1 is XOR with a block of low ones. A valid square needs b_j ⊕ b_{j+1} = 1 and a
  pattern 0 1…1 0 in the low bits of a_i ⊕ b_j, with a_i ⊕ a_{i+1} = 11…10. Count with a map or
  trie per bit length. O(m log V). Tags: bits, hashing.
- **Attempts:**
  1. 3192569 (184.4') WA: `mp[b[i]]++` keys the map by the full value instead of the low bits.
  2. 3192839 (226.6') WA: masking fixed (`mp[b[i] & mask]++`), a brute force plus random tester
     added. But the main loop is **`for(int l = 0; l < 3; l++)`**, reduced for the small-value test
     (`test(5, 10, 10)`) and never restored to 30.
  3. 3196588 (next day, upsolve) AC: `l < 30`. The algorithm was correct in the contest.
- **Lesson:** a pre-submit checklist item: "remove or restore every test-only change (loop bounds,
  `test()` calls, debug prints)". This single character cost a 4th problem (#127 → #86).

### M. Replacement — field 248/260 (cf 1444) — **AC 32.6' after 2 WA** (Dedi)
- **Idea:** only replacement positions near the ends can be optimal (exactly 2, 3 and n−1, per the
  editorial). Enumerate O(1) positions and compare the results **as numbers**. Tags: greedy/casework,
  big binary strings.
- **Attempts:**
  1. 3191371 (21.3') WA: tries positions 2 and n−1 and picks the best with `mx = max(mx, t)`, a
     **lexicographic** comparison of binary strings ("11" > "100").
  2. 3191395 (27.2') WA: adds position 3. Still a lexicographic max.
  3. 3191415 (32.6') AC: compares by length first (`mx.size() < t.size() || …`) and adds n−2.
- **Lesson:** two bugs at once, both caught only by the judge: a string comparison that is not a
  numeric comparison, and a candidate set guessed one position at a time. A brute force over all
  positions for |s| ≤ 12 would have found both in a minute.

## Takeaways from this contest
1. **Penalty disaster on easy problems:** 12 wrong runs on the three easiest problems (240 min).
   Each chain shows the same pattern: resubmitting variations instead of testing locally (G
   toggling, M guessing positions, B patching edge cases one by one).
2. **Missing verification idea (B)**, typical of counting/constructive problems: "the independent
   choices must be checked globally".
3. **Test-mode leftovers (J)**: the clearest single cost in the season so far, a 4th problem.
4. **No pairing during chains.** Three members were each stuck alone at the same time.
5. Good sign: Dedi's J approach was right, and the brute-force tester was used (the habit exists).
