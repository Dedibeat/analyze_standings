## Problems (solved)

### A. It Is Late at Night, Remember to Rest — field 369/369, cf 821 — **AC 9', first try** (Dedi)
- "yeshenle" can only be sent 00:00–00:59 and "zaoshanghao" only 07:00–07:59; find the fewest
  days a chat log spans. Our greedy starts a new day whenever a "yeshenle" follows a "zaoshanghao"
  of the current day. Fine; 3 min behind the gold median.

### K. Salary Adjustment — field 232, cf 1948 — **AC 57', first try** (Dedi)
- Count the orders (mod 998244353) in which employees switch from salary a_i to b_i so that a
  superior never earns less than a subordinate. Our code keeps the edge i–f_i only when it forces an
  order: b_i > a_f (f must go first) or a_i > b_f (i must go first). It then counts the orders of the
  resulting forest with the hook-length product dp[u] = (sz_u − 1)! · ∏ dp[v] / sz_v!, treating every
  kept edge as parent-first.
- That shortcut is correct, and Dedi saw why during the contest (user, 2026-11-22): reversing an
  order maps the "child first" count onto the "parent first" count. It also needs each component to
  point one way, which holds: both ends of a "parent first" edge strictly increase, and both ends of
  a "child first" edge strictly decrease. Our code matches a brute force on 400 random trees of ≤ 6
  employees (scratch harness). Clean and first try, ahead of the gold median.

### D. Travel Plan — field 328, cf 1628 — **AC 94.5' after 3 wrong runs** (Tamir 2 WA, then Dedi RE, AC)
- Given a simple connected graph and the depth a_v that a recursive DFS must give each vertex,
  output a start vertex and an order of every adjacency list, or −1. Dedi's AC: the unique vertex with d = 0 is
  the root; in every list put the neighbours with d = d_i + 1 first, run the DFS, and print −1 unless
  it reproduces d.
- **Tamir, 3504949 (42') and 3505004 (53').** He checked necessary conditions: one d = 0 vertex,
  and every other vertex has exactly one neighbour one level up. The second run added "no neighbour
  at the same level". He then printed children-first lists **without running the DFS** to see whether
  the order really gives d, and there is no check that would replace that. Stress test (3,000 random
  graphs of ≤ 7 vertices; scratch harness, not in the repo): the first run is wrong on 10 cases
  (e.g. two depth-1 vertices joined by an edge), the second on 3.
- **Dedi, 3505158 (75') RE: the "unknown bug in sorting".** The children-first order was made with
  `sort(all(g[i]), [&](int u, int v){ return d[u] == d[i] + 1; });`. That comparator is not a strict
  weak ordering: it returns true for (u, u), and says u < v and v < u for two children. `std::sort`
  with such a comparator is undefined behaviour and can run past the array, hence the RE. A
  `-D_GLIBCXX_DEBUG` build of this exact code aborts inside `std::sort` on 2,264 of the 3,000 random
  graphs. The AC (3505335) builds the two groups by hand, a stable partition, and also brings a
  random tester (`test()`). The fix was right; the tester came after the RE.
- **Lessons.**
  - When the output must make an algorithm behave a certain way, **simulate it and compare** before
    printing; that check is the whole proof.
  - A sort comparator answers "strictly before", never "is good". To put good items first, use
    `stable_partition` or compare `key(u) > key(v)`.
  - In both cases a 30-line brute force plus a checker on graphs of ≤ 6 vertices finds the bug in
    seconds.

### G. Shuffle Playlist — field 95, cf 2328 — **AC 187.5', first try** (Erdene)
- n songs; song i uses one of a_i cards, else one of k blank cards, else playback stops. The
  playlist is reshuffled (that song first, the rest in any order) whenever its last song is about
  to play, so a song never repeats back to back. Find the most songs played with the best shuffles.
- Our code sorts a and takes the number of full rounds c = min over prefixes of
  ⌈(prefix sum + k − 1)/i⌉, capped by 2(a_1 + k). It answers c(n − 1) + 1, extended from the top
  while the blank-card budget b ≤ c − 1 + k holds and capped at (c + 1)(n − 1). Without an
  editorial the formula is not proved here; it is AC.
- **Three ACs.** 3506362 is the first AC. 3506369 (25 s later) drops the `mn` condition and 3506418
  (5 min later) also drops the template macros: the same solution trimmed twice. Erdene resubmitted
  to make his own code shorter (user, 2026-11-22). Resubmissions after an AC cost no penalty.
- Erdene arrived late and worked G alone for about two hours. 30 min behind the gold median, ahead
  of the silver median.

### J. Number Game — field 117, cf 2239 — **AC 226', first try** (Dedi, with Tamir)
- One operation replaces any chosen numbers of the multiset A by the mex of the chosen ones. Can A
  become B?
- Our code counts B, sorts its (value, count) pairs by value − count, and absorbs pairs from the
  smallest while value − count ≤ the absorbed total: those values can be produced by mex

### B. When Does BPE Stop Doubling? — field 55, cf 2442 — **AC 297' after 3 WA, not counted** (Dedi)
- Each corpus string is n_i zeros (n_i given in binary, up to 200,000 bits). BPE merges the most
  frequent pair each round; find the first mixed rule [x, y] with x ≠ y, the number k of
  self-merges before it, and its frequency.
- Our idea: after j self-merges, a string of n zeros is n >> j copies of token j followed by one
  token per set bit of n below j. So for each round j (tried from max length − 20 to max length + 5)
  the code compares the count of [j, j] pairs, capped at 10^6, with the most frequent mixed pair
  of adjacent set-bit tokens.
- **The bug: an out-of-bounds read.** `for(int i = 0; i < j; i++) if(s[i] == '1') ...` runs j up to
  max length + 5, so for every shorter string it reads `s[i]` past `s.size()`. That is undefined
  behaviour, and in practice it reads leftover bytes, which can be '1'. The AC (3507736) changes the
  bound to `min(j, (int)s.size())` (and caps cnt at 10^6, which made no difference in testing).
- **How the three WAs were spent:** 3507578 (284') was the first version. 3507636 (289') added an
  early `-1` when check() returns empty, and 3507673 (292') moved the cut's lower bound from 0 to 1.
  Both were logic changes: the logic was right, and the bug was not in it.
- **Verified** (scratch harness, 2,000 random multi-case inputs of n up to 26 bits): the last
  WA differs from the AC on 148; built with `-D_GLIBCXX_ASSERTIONS`, the same code aborts at
  `s[i]` on 1,880. **One compile with assertions finds this bug at the first run of a random test.**
- Dedi did not expect an out-of-bounds read to cause a WA rather than an RE. It usually does not
  crash: reading a few bytes past a short string stays inside the heap, so the program just uses
  garbage.

## Takeaways from this contest
1. **One bounds check was gold.** B's code was right apart from `i < j` instead of
   `i < min(j, s.size())`. Rule for the last hour: on a WA whose logic you believe, first rerun the
   samples and a random test with `-D_GLIBCXX_ASSERTIONS` (and `-fsanitize=address,undefined` where
   the machine has it) before changing any logic.
2. **D cost 60 penalty minutes and an hour of the start.** Two runs without checking the output by
   simulation, then a comparator that was not an ordering. Both would have been caught by a brute
   force or checker on tiny graphs, and the AC run shows Dedi writes one quickly.
3. **The strong parts.** A and K first try, K ahead of the gold median; G and J first try. Only one
   problem (D) had wrong runs before AC in the counted result.
4. **The middle hour is where the medal went.** From 94' to 187' nothing was submitted, and J took
   two people 131 minutes. G and J came in at silver pace, not gold pace.
5. **The minute-200 rule worked as a choice** (B, the gold teams' 6th problem) but not as a finish:
   the plan's "one person explains, another tries to break it" step would also have covered B's
   runs 2 and 3.
