## Problems

### A. Average of Averages — field 11/319 (Mid) — not attempted
- **Idea:** divide and conquer over the segment tree. At node [l,r] count crossing intervals with
  S_left(L) − L = R − P_right(R) using a hash map. Nodes of equal length are equivalent, so memoize
  by length. Multiply by a large power of 2 to stay in integers. Tags: D&C, hashing, math.
- **Missed?** Rarely solved onsite (11). Skipping it was correct for a 6–7 solve team.

### B. Bouncing Particles — field 1/319 (Mid-Hard) — not attempted
- Reflections become extra diamond-shaped (rotated-square) wavefronts released at the boundary hits.
  Intersect the query line with ≤ 20 diamond edges and deduplicate. Heavy casework geometry.
  Correct skip.

### C. Counting Arrays — field 129/319 (Easy-Mid) — **AC 117' after 4 WA** (Dedi)
- **Idea:** between consecutive constraints at distance ℓ, the increments that occur inside the
  segment contribute distinct values in 1..ℓ. So "c increments adding w to the sum" = number of ways
  to choose c distinct numbers from 1..ℓ summing to w. Precompute that table by 0/1 knapsack
  (O(n⁴)), then DP over the value a_R at each constraint position. Tags: counting DP, knapsack.
- **Attempts** (all `data/team_r3/code/`):
  1. 3333640 (31') **wrong idea + misread modulus.** It multiplies independent segment counts,
     `ans = ans * dp[dlen][dval] % mod`. That ignores the dependence on a_L. And
     `const int mod = 1e9 + 7;` although the statement says 998244353.
  2. 3334409 (83') **right idea, still the wrong modulus.** It now does a DP over the value at each
     constraint with a 3-D table `dp[len][cnt][sum]`, exactly the editorial's method. It also indexes
     `dp[dlen][dj][dif]` with `dif` up to 10^9, out of bounds.
  3. 3334633 (103') adds `if(dif < 0 || dif > lim) continue;` (bounds fixed) and writes a brute
     force plus a random tester (`test()`, `brute()`). Good practice, but the brute was itself
     wrong, and the modulus was still 1e9+7.
  4. 3334766 (112') finally `const int mod = 998244353;`. Still WA:
     `ans = accumulate(all(dpcur), 0LL);` is never reduced, so it prints an unreduced sum when the
     last constraint is at position n (tail = 0).
  5. 3334853 (118') `accumulate(...) % mod` → AC.
- **Cost:** 80 penalty minutes plus 86 minutes of wall time on an Easy-Mid problem. The decisive bug
  class is **reading the statement's constants** (modulus): it survived three submissions.
- **vs editorial:** same algorithm. But `int dp[105][105][10005]` with `#define int long long`
  used **810 MB** (QOJ reports 809,916 KB). The QOJ statement text does not state the memory limit;
  under any limit below ~810 MB (512 MB is common onsite) the AC would be MLE. Bounding sum by
  n(n−1)/2 = 4950 and using 32-bit ints makes it ~200 MB.

### D. Duel of Wrath — field 312/319 (Easy, 394-byte reference) — **AC 79' after 3 WA** (Erdene)
- **Idea:** the damage taken is always S·b and S·a for the same S. B survives the previous rounds
  only while S·a < h_B, so S ≤ ⌊(h_B−1)/a⌋. The last round adds at most 4. Answer YES iff
  h_A > (⌊(h_B−1)/a⌋ + 4)·b. Tags: math, worst-case reasoning.
- **Attempts:**
  1. 3333931 (50') **wrong model**, reasoning from A's health: `int k = (ha - b4 + b - 1) / b;
     ... hb -= k * a;`. It also overflows (`k * a` up to 10^36).
  2. 3334026 (55') patches an edge case of the same wrong model (`if(ha <= 0 && hb <= 0)`).
  3. 3334250 (72') **correct formula**, `int k = (hb + a - 1) / a - 1;
     if(ha - b * (k + 4) > 0)`. But `b * (k + 4)` overflows 64-bit (b, k up to 10^18).
  4. 3334375 (80') `if((__int128_t)ha > (__int128_t)b * (k + 4))` → AC.
- **Lesson:** the easiest problem of the set cost 60 penalty minutes and 30 minutes. Two attempts went
  in before the invariant ("damage is S·b vs S·a") was found. The last bug was the classic
  "constraints are 10^18 and I multiply two of them". **Rule:** if any input is ≥ 10^9, check every
  product before submitting.

### E. Enclose the Point — field 31/319 (Mid) — **failed, 5 in-contest runs** (Dedi)
- **Idea:** take the convex hull. No answer unless Q is strictly inside it. Fan-triangulate from one
  hull vertex A and binary-search Q's wedge. If Q is strictly inside a fan triangle, that triangle is
  the answer. If Q is on a diagonal AX, take one hull vertex on each side; among those ≤ 5 points
  some triangle strictly contains Q. The only 4-gon case: the hull has 4 vertices, Q is the diagonal
  intersection, and every point lies on the two diagonal lines. Tags: convex hull, casework geometry.
- **Our approach** was the editorial's skeleton (hull, fan binary search, a few candidate
  triangles, the special 4-hull case). It had **three implementation bugs**. I found them by
  stress-testing our code against a brute force (random points in [−3,3]², scratch harness, not in
  repo):
  1. **Orientation-dependent point-in-triangle.** `intri` does `sort(p.begin(), p.end())` and then
     tests fixed signs, `if(a < 0 || b > 0 || o < 0) return -1;`. That is only right when the
     middle-x vertex lies above the line through the other two. Counterexample: points
     (−3,2),(1,−3),(3,−3),(1,1),(−3,3) with Q=(0,−1). Q is strictly inside hull triangle
     (−3,2),(1,−3),(3,−3), but every candidate is rejected and the code falls through.
  2. **`out()` sorts the vertices by coordinate before printing.** For a quadrilateral answer this
     prints a self-intersecting polygon.
  3. (in-contest versions only) On a 4-vertex hull with `spec == -1` (all points on the diagonal
     lines) it printed the whole quadrilateral without first trying triangles. That is wrong when Q
     is on only one diagonal. The 312' upsolve (3336988) fixed this one.
  - With fixes 1 and 2, the upsolve code passes 14,000 random cases. So the contest code was about
    **three local fixes from AC**, with the approach right.
- **How the runs were used:** 3336557 TL / 3336569 RE / 3336583 TL / 3336638 WA / 3336649 WA. They
  were judge-as-assert probes: `for(;;);` (TL) and an `int ass(int x)` helper that never returns
  (UB → RE) were placed in "impossible" branches. Attempt 5 even deleted the fallthrough
  `cout << "-1\n";`. Probing showed *that* a branch was reached, not *why*. A 30-line brute force on
  tiny coordinates finds bug 1 in under a second.
- **Lesson:** the 7th problem and probably ~#10–16 were lost to **geometry glue code without a
  local stress test**. A team geometry template (orientation-safe point-in-triangle /
  point-in-convex-polygon) would have removed bug 1 entirely.

### F. First Word — field 0/319 (Mid-Hard) — not attempted
- Words valid ⇔ one chosen word is a prefix of all others → suffix-automaton (on reversed S) subtree
  counting; Σ_u [C(D_u,k) − C(D_u−d_u,k)] needs power sums via polynomial log of ∏(1−X_u x) and a D&C
  falling-factorial conversion, O(n log² n). Correct skip.

### G. Graph Reconstruction — field 9/319 (Mid) — not attempted
- Handshake-lemma algebra: e_ij = a_ij + E(G) − E(H_i) − E(H_j); E(H_i) = (r_i − deg_{H_i}(1))/(n−4);
  enumerate deg(1) (≤ 6 checks), brute force n ≤ 5. Tags: math/constructive. Rare onsite; fine skip.

### H. Hidden Order — field 26/319 (Mid, 899-byte reference) — **AC 286', first try** (Erdene)
- **Idea:** deque pass: compare the new index with the back; "greater" goes to the front, otherwise
  to the back. One pass collects all maxima at the end. A second pass over the rest sorts it.
  Exactly (n−1)+(n−2) = 2n−3 queries. Tags: interactive, constructive.
- **Ours:** 3336780 is exactly the editorial's first solution (two deque passes, final
  `ans.push_back(dq.back())`), 1.2 KB. A clean, first-try solve of a problem only 26 official
  teams solved. This was the contest's best moment.

### I. Invisible Edges — field 131/319 (Easy-Mid) — **AC 156', first try** (Erdene)
- **Idea:** DFS bracket sequence: a_u = position of u's opening bracket in [1,2n]. The decoder
  scans positions 1..2n with a stack (present value = push and connect to the top; absent = pop).
  Tags: communication (two-run) problem, DFS/Euler tour.
- **Ours:** 3335354 is identical to the editorial (`res[u] = timer++` on entry, `timer++` on exit;
  stack decode). Clean.

### J. Joint Relocation — field 0/319 (Hard) — not attempted. Correct skip.

### K. Keep Your Distance — field 219/319 (Easy) — **AC 93', first try** (Tamir)
- **Idea:** binary search d. The feasible set for b_i is [a_i−d, a_i+d] ∩ ((−∞, mx−l] ∪ [mn+l, ∞)),
  and only its min and max matter. O(n log w). Tags: binary search, greedy interval propagation.
- **Ours:** 3334524 is the editorial's method (keeps `seg[i+1] = {mn, mx}`). Correct, first try.
  Leftover commented-out code from a discarded two-endpoint idea (`can[i][0]`) shows the first idea
  changed mid-implementation; harmless.

### L. Long Slides — field 0/319 (Hard) — not attempted. Correct skip.

### M. Minimum Records — field 283/319 (Easy) — **AC 23', first try** (Erdene)
- **Idea:** greedy: a new record always takes its r_i; when some l_i exceeds the current max, the
  segment since the last record must add one record, and the best choice is the largest r in it.
  O(n). Tags: greedy.
- **Ours:** 3333553 is the editorial's greedy (`cur = max(mx, a[i].second); ans++`). Fast and clean.

## Takeaways from this contest
1. **Easy-problem chains decided the medal.** D (overflow + 2 wrong models) and C (wrong modulus
   ×3, unreduced sum) cost 140 penalty minutes. Gold was 59 minutes away.
2. **The modulus was copied from habit, not from the statement**: 1e9+7 in three consecutive C runs.
3. **Geometry implementation, not ideas, lost E** (Dedi). The approach matched the editorial. The
   point-in-triangle helper was orientation-dependent and the output routine sorted vertices.
4. **Strengths seen:** clean first-try solves of interactive (H) and two-run communication (I)
   problems, and a correct binary-search-plus-feasibility (K). Erdene solved 4 of the 6.
5. C's brute-force tester shows the right instinct. It came after two WAs and had its own bug.
